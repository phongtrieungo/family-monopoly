# B-09 · Wider-playtest review

Review date: 2026-11-06. Reviewer: Codex, examining the repository and existing internal evidence. This is an engineering review of readiness. It does not grant legal clearance or replace a fluent Vietnamese reader, accessibility tester, physical-device testing or family playtest. The owner reported that local play was good so far; no full-match outcome, participant count or device coverage was supplied for that report.

## Current decision

Continue internal testing. Do not treat the project as cleared for a wider or public playtest until the open gates below have named reviewers and recorded results. B-09's review is documented; the wider-playtest gate remains open. The local original-content game and the synthetic private-room prototype have different UI coverage, so evaluate them separately.

## Review findings and open gates

| Area | Evidence and current finding | Gate before wider playtesting |
| --- | --- | --- |
| Branding and distribution | The game uses the authored name “Phố Nhà Mình,” original board labels and system fonts; [the licensing manifest](research/licensing.md) records the source of current material. The underlying game uses a selected C1009 rules baseline. No name search, trademark opinion or distribution permission is documented. | Obtain an appropriate branding and distribution review for the proposed audience and scope. Record the reviewer, date, results and any required changes in the manifest. Do not represent the original board or text as an official Vietnamese edition. |
| Vietnamese localization | Labels, card copy and UI copy are project-authored and use Vietnamese diacritics. The local screen identifies its content as an internal draft. Fluent-reader approval is not recorded. | A fluent Vietnamese reader reviews terminology, instructions, all 40 space labels, 32 card texts, errors, handoffs and debt/trade descriptions in context. Record proposed corrections and owner decisions before promotion. |
| Accessibility | [B-06](prototype-acceptance.md) and [B-10](local-play.md#browser-acceptance-runner-and-evidence) record keyboard and emulated touch checks, reduced-motion mode, focus and a space list. B-09 found that the local list omitted occupants shown on the visual board; the local list now identifies the occupants and active seat's location, covered by AC-38. These checks do not establish screen-reader, low-vision, motor-accessibility or physical-device conformance. | Review keyboard focus through all decision forms, screen-reader announcements and labels, zoom, contrast and touch target sizes on real desktop and phone devices. Record device/browser, assistive technology, results and issues; fix or explicitly defer issues before widening access. |
| Retention and credentials | `src/rooms/file-store.js` stores room state, seat sessions, command receipts and event history in a private file; files are written with mode 0600. The browser stores local sessions, the latest public snapshot and pending commands in session storage. `src/web/server.js` creates a temporary directory by default; no automatic deletion, retention deadline, backup or cleanup is implemented. A configured `ROOM_STORE` remains on disk until manually removed. Starting a new local game removes the browser's reference but does not delete the old room record. The default store path is not automatically rediscovered after a server restart; temporary files may remain on disk. | Before wider deployment, choose and document retention periods, deletion and backup handling, access controls and an operator-owned cleanup process. Verify deletion of room records, receipts, credentials, temporary files and backups together. Do not promise automatic deletion until it exists and is tested. |
| Abandonment and disconnect | The current prototype pauses a pending decision on disconnect. It has no decision timer, automatic pass, host succession or match abandonment action. A local game can be replaced in the browser after confirmation, while the server record remains. A private-room host may close a lobby before a match. | Decide who may end an abandoned match, when, how pending debts or auctions are handled, how players are informed and how retained data is deleted. Update digital policy, scenarios and tests before implementing automatic action or cleanup. Preserve reconnect and idempotency requirements. |
| Balance and real play | The original economy and cards are authored content; automated acceptance uses fixed dice and saved decision fixtures. The owner's positive report is useful feedback but does not establish balance or a complete-match result. | Record complete games with 2, 3 and 4 people, decisions that cause confusion, duration, outcomes and rule/balance feedback. Pin the content version and avoid storing credentials or unrevealed deck order in shared evidence. |

## Review procedure

1. Assign a reviewer and record the audience, device or distribution scope for each open gate above.
2. Use the current [local-play acceptance procedure](local-play.md#browser-acceptance-runner-and-evidence) and [prototype acceptance procedure](prototype-acceptance.md) as reproducible starting points; add physical devices and assistive technology rather than treating emulation as evidence for them.
3. Record findings and decisions with dates and links to affected requirements, rule IDs and scenarios. Keep C1009 evidence and digital policy separate. For behavior changes, update the specification and scenarios with the implementation.
4. Reassess the gate after the open reviews are complete. A successful internal automation run or a single informal play session alone does not establish wider-playtest readiness.
