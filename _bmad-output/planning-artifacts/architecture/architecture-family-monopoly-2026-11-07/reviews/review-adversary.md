# Adversarial seam review

Verdict: revise before finalization. Independently compliant implementations can diverge at these seams:

1. **Receipt identity and replay:** AD-2 omits the receipt's scope and original-result contract. One service can deduplicate globally by command ID while another scopes it to a room and seat; both satisfy the text, but a command ID reused by a different seat can be rejected or incorrectly return another seat's receipt. `specs/rooms.md` explicitly scopes deduplication by room and seat and returns the original result for an identical retry. Bind the scope, command identity and exact receipt replay.
2. **Recovery and in-flight commands:** AD-6 requires invalidating a session and issuing a new one, but does not say whether seat identity, receipts and the pending command survive that rotation. A recovery service could create a new seat while a command service scopes receipts to the old seat; a retry after an accepted response was lost could charge twice. Bind recovery to the existing stable room/seat identity and preserve receipt scope and outcomes across session rotation; serialize the credential replacement against room commands.
3. **File-store ownership:** AD-2 requires per-room serialization, but `src/rooms/file-store.js` replaces the entire rooms collection on every write. Two room services could each serialize writes to their own room and still overwrite another room's newer state. Bind atomic isolation across all rooms sharing a whole-file store, or explicitly prohibit concurrent writers until the store provides isolation. A single process alone is insufficient if concurrent asynchronous transactions are introduced.
4. **Room profile dispatch:** AD-1 preserves pinned content, but leaves the mechanism that interprets a persisted room's profile outside the invariants. Two compliant room handlers could route the same stored profile to different reducers after restart. Require server-side lookup by the room's immutable profile/version pin, reject unknown or unsupported versions, and never accept the client as profile authority. This is especially important because EPIC-003 S1 explicitly requires versioned dispatch while the current service binds one profile at construction.
5. **Event and snapshot visibility:** AD-3 disallows hidden fields but does not require a common visibility boundary for revisioned events and snapshots, or require the same authorization for history retrieval. One handler could redact snapshots while returning unredacted accepted event payloads. Require authorization and permitted projections for both snapshots and history; preserve revision ordering without exposing internal continuations.
6. **Recovery-code response loss:** AD-6 permits a recovery endpoint that invalidates the old session before the response reaches the new device. It leaves unspecified whether the same recovery code can be retried or whether it is rotated atomically, so a lost response can strand a player despite possessing the code. Resolve code lifetime/rotation and recovery idempotency together before implementation; document it as a blocking design decision if owner intent is insufficient. No need to mandate a particular cryptographic protocol in this spine.

Existing limitations are correctly labeled: the synthetic private UI, temporary default storage, open retention policy and B-09 review gates. The user chose recovery codes but did not authorize deployment or define a provider.
